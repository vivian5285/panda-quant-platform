## 修订说明（请Cursor开发前先读这一段）

v2.0版本存在两处容易被字面误读、导致实现出错的表述，v3.0已经用明确公式和数值算例替换。如果你此前已经开始基于v2.0实现，请对照本节重新核对：

1. **雷达启动阈值"TP1 × 0.85"——这不是"TP1价格乘以0.85"，而是"距离TP1还剩15%时启动"**。TP1在Webhook消息里是一个绝对价格（比如1900.23），如果直接拿0.85去乘这个绝对价格，算出来的数字和开仓价毫无关系，是错误实现。正确算法见第四部分4.1。
2. **重入后的雷达启动阈值，不再是0.85，而是1.00（价格必须真正走到TP1才启动）**。这是本版新增规则，原因见第四部分4.1和第五部分5.4。
3. **硬止损呼吸垫系数，不再按弱/中/强三档区分，改为统一固定值1.15**，适用于ETH和XAU两个品种、所有档位。原因见第三部分3.2。

## 第一部分：设计哲学

### 1.1 核心思想转变

策略回测已经证明了方向判断和胜率没有问题。ETH盈利因子达到14.177，XAU盈利因子达到15.393。真正限制利润的是执行层过早干预，而不是策略本身的问题。

因此雷达的角色从主动锁利、防止回吐转变为被动跟随、守护趋势。入场靠评分系统，出场的利润兑现靠TP结构，雷达的职责是防止趋势被过早打断，而不是频繁判断方向。

### 1.2 三个层级各司其职

- **TV策略**是总指挥，负责判断方向、决定入场和出场时机。
- **硬止损**是最后防线，确保任何情况下单笔亏损可控。
- **雷达**是骑士守卫，在TP1之前不介入，TP1之后跟随趋势上移止损，不主动判断方向。
- **TP1、TP2、TP3**负责利润兑现，逐级兑现利润，TP3占比百分之七十负责大肉部分。
- **重入机制**是补救措施，仅在雷达被噪音扫出时触发一次，以更优价格重新进场。

### 1.3 为什么TP3占比百分之七十

TP1和TP2负责兑现小利润，TP3负责搏大趋势。如果TP3占比太低，大趋势来临时只有少量仓位能吃到利润。高占比的TP3让策略在趋势行情中有足够的仓位暴露，同时通过雷达的动态保护来控制回撤风险。

### 1.4 不再神经质的雷达

雷达不再提前介入、不再快速上移止损、不再频繁判断要不要走。价格走到TP1附近才启动，在TP1到TP2之间保持宽松跟踪，在TP2到TP3之间逐步收紧，在TP3之后转为动态追踪直到趋势终结。雷达只是在价格不断创出新高的时候跟着抬高止损，而不是在价格还没走多远的时候就锁住利润。

## 第三部分：硬止损计算逻辑

### 3.1 计算方式（完整公式，Cursor请严格按此实现，不要自行简化）

```
第一步：计算TV止损距离（不是止损价本身，是"距离"）
tv_stop_distance = abs(webhook消息.price - webhook消息.stop_loss)

第二步：叠加呼吸垫系数，得到VPS实际要用的止损距离
actual_stop_distance = tv_stop_distance × 1.15

第三步：以VPS自己的实际成交价为锚点计算硬止损价格（不是TV的price字段）
多单：硬止损价 = VPS实际成交价 - actual_stop_distance
空单：硬止损价 = VPS实际成交价 + actual_stop_distance
```

**数值算例（帮助Cursor自测）：**

假设ETH多单，TV消息里`price=1900.00`，`stop_loss=1874.00`。
- `tv_stop_distance = |1900.00 - 1874.00| = 26.00`
- `actual_stop_distance = 26.00 × 1.15 = 29.90`
- 假设VPS因滑点实际成交价是`1900.80`
- `硬止损价 = 1900.80 - 29.90 = 1870.90`

注意最终硬止损价（1870.90）比TV原始止损价（1874.00）更宽，这是呼吸垫和滑点共同作用的结果，符合设计预期，不是bug。

### 3.2 呼吸垫系数【本版修正：不再分档，统一为1.15】

**v2.0曾按弱/中/强三档分别设置1.1/1.2/1.3，本版废止这个设计，原因如下：**

TV策略这边的止损距离本身已经按趋势强弱分档（弱趋势用更紧的距离，中/强趋势用更宽的距离，这是策略层面对"行情性质"做的判断）。VPS这层呼吸垫的本意，是补偿"K线闭合发出信号"到"VPS实际完成开仓"这段执行链路上的滞后与滑点——这是**执行层面的固定摩擦**，和这笔交易属于强趋势还是弱趋势没有直接关系。

如果VPS再按档位放大一次，两层叠加之后，强趋势的实际止损宽度会被放大到弱趋势的1.5倍以上，超出了"补偿执行摩擦"这个原始设计意图，变成了对TV那边已经做过的档位判断又做了一次无意的二次加权。

**因此本版规则：呼吸垫系数固定为1.15，适用于ETH和XAU两个品种、所有档位，不再查表。**

这个1.15是起始值，不是永久值。请按第十一部分11.3节的要求，在实盘小仓位验证阶段，收集"TV止损距离"与"实际触发止损时的真实滑点"这两组数据，用真实数据校准这一个数字，而不是继续按趋势强弱去猜测。

### 3.3 异常处理

如果Webhook消息中没有`stop_loss`字段，或者字段值为零或负数，禁止开仓并记录错误日志。如果计算出的`tv_stop_distance`小于该品种最小价格变动单位（tick size）的五倍，同样视为异常数据，拒绝开仓并记录日志。

### 3.4 硬止损的生命周期

硬止损在开仓成交后立即挂出，从挂出到仓位归零之前绝对不撤销、不修改、不替换。它和雷达止损同时存在，相互独立。唯一撤销硬止损的时机是仓位归零的那一刻。

### 3.5 建议（可选，非强制）：Webhook补充档位字段

当前TV传给VPS的开仓消息不包含"当前是弱/中/强哪个档位"这个信息，VPS要判断第四部分的档位相关参数（跟踪步长、每次跟进幅度、呼吸空间），目前只能靠VPS自己重新用ATR和价格反推档位，这存在和TV两边判断不一致的风险。

**建议**：如果TV策略脚本方便调整，在开仓消息JSON里补充一个`tier`字段（取值0/1/2），VPS直接读取即可，不需要自己重新计算档位，能从根本上避免"TV判定强趋势，VPS却算成中趋势"这类不同步问题。如果短期内TV脚本不方便改动，VPS可暂时用`tv_stop_distance`相对该品种`atr`字段的比例反推档位，作为过渡方案，但应在后续迭代中优先切换到直接读取`tier`字段。

## 第四部分：雷达逻辑

### 4.1 启动机制【本版修正：明确公式，区分首次开仓和重入开仓】

**核心澄清：这里的"0.85"和"1.00"，作用对象是"距离"，不是"价格"。**

```
第一步：计算TP1的距离（不是TP1的绝对价格本身）
tp1_distance = abs(webhook消息.tp1 - webhook消息.price)

第二步：根据"这是首次开仓还是重入开仓"，选择启动系数
首次开仓：activation_ratio = 0.85
重入开仓：activation_ratio = 1.00   （本版新增，见5.4说明原因）

第三步：以VPS实际成交价为锚点，计算雷达激活的触发价格
多单：雷达激活价格 = VPS实际成交价 + tp1_distance × activation_ratio
空单：雷达激活价格 = VPS实际成交价 - tp1_distance × activation_ratio

第四步：激活条件（每次价格更新都要检查）
多单：当前价格 >= 雷达激活价格 时，雷达介入
空单：当前价格 <= 雷达激活价格 时，雷达介入
```

**数值算例（首次开仓，帮助Cursor自测）：**

ETH多单，`price=1900.00`，`tp1=1925.65`，VPS实际成交价`1900.80`。
- `tp1_distance = |1925.65 - 1900.00| = 25.65`
- 首次开仓：`雷达激活价格 = 1900.80 + 25.65 × 0.85 = 1922.60`
- 价格涨到1922.60时，雷达介入；在此之前，只有硬止损在保护仓位。

**数值算例（重入开仓，同一笔信号）：**

- 重入开仓：`雷达激活价格 = 重入成交价 + 25.65 × 1.00`
- 也就是说重入这一笔，必须价格真正涨到TP1的位置，雷达才会介入，比首次开仓时晚一些才接管。

在价格到达启动条件之前，雷达完全不介入，只有硬止损在保护仓位。价格到达启动条件时，雷达接管仓位，并将止损从硬止损位置上移至开仓价加减0.5倍ATR。

### 4.2 为什么重入要把启动阈值从0.85放宽到1.00

重入本身就是"上一次被噪音扫出、这次用更优价格重新进场"的补救动作。如果重入这一笔仍然沿用0.85这个和首次开仓一样紧的启动阈值，很可能重蹈上一次被过早扫出的覆辙，让重入机制的价值打折扣。放宽到1.00（价格必须真正走到TP1才启动雷达），本质上是给重入这一笔更多呼吸空间，和"重入本来就是为了少一点神经质"这个设计初衷保持一致。

### 4.3 跟踪机制

雷达激活后只做一件事：价格每涨一段，止损就跟进一段。跟踪步长和每次跟进幅度由当前档位决定，档位不同则步长和幅度不同（参见第二部分2.2、2.3的参数表）。雷达不主动判断方向，不决定何时离场，只在价格创出新高时抬高止损。

### 4.4 呼吸空间动态调节

在TP1到TP2之间保持宽松跟踪，TP2到TP3之间逐步收紧，TP3之后转为动态追踪。弱趋势档位使用较紧的呼吸空间，强趋势档位使用较宽的呼吸空间，所有参数根据当前档位自适应调节。

### 4.5 雷达与硬止损的关系

两笔止损单同时存在，各自独立运作。价格触发雷达止损时，仓位归零后硬止损自动撤销。价格直接击穿硬止损时，仓位归零后雷达止损自动撤销。两层保护互不干扰，谁先触发谁执行。

## 第五部分：重入机制

### 5.1 触发条件（必须同时满足全部条件）

1. 平仓来源是雷达扫出，**硬止损扫出绝对不触发重入**。
2. 平仓价格必须落在允许区间内：
   - ETH多单：开仓价 到 开仓价 + 0.5倍ATR
   - XAU多单：开仓价 到 开仓价 + 0.3倍ATR
   - 空单对称（方向相反）
3. TV信号必须仍然有效：未收到反向信号（LONG/SHORT）或平仓信号（CLOSE_QUICK_EXIT/CLOSE_RSI_EXIT）。
4. 该方向信号下累计重入次数为零（最多一次，不可重复）。

### 5.2 重入窗口期

从雷达扫出到触发重入请求的时间必须在窗口期内：
- ETH窗口期：2根K线，约3小时
- XAU窗口期：3根K线，约2.25小时

超过窗口期则放弃本轮重入，不再尝试。

### 5.3 重入价格计算

```
多单重入价 = min(5分钟最低价 + 1个tick, TV信号价 × 0.997)
空单重入价 = max(5分钟最高价 - 1个tick, TV信号价 × 1.003)
```

如果5分钟K线数据不可用，使用3分钟K线作为备选。**重入价格必须优于上一次开仓价，否则不触发重入**（多单要求重入价更低，空单要求重入价更高）。

### 5.4 重入后的雷达系数与启动阈值

重入成功后，跟踪步长和每次跟进幅度使用当前档位对应的雷达系数，但选择**比首次开仓宽松一档**，避免在同样的噪声水平下再次被扫出（比如首次开仓判定为中趋势档位，重入后按强趋势档位的跟踪参数执行）。

**雷达启动阈值：重入这一笔固定使用1.00（不是0.85），见第四部分4.1、4.2**。

档位递进只在重入成功时发生，不影响TP1、TP2、TP3限价单的价格和数量——这些依然使用TV在原始信号里传来的价格，不因重入而改变。

### 5.5 不允许重入的情况（任一条件命中即终止）

- 硬止损平仓，绝对不重入。
- 亏损平仓（平仓价低于开仓价，多单场景），不重入。
- TV已发出平仓或反向信号时，不重入。
- 超过窗口期，不重入。
- 已经重入过一次，不再重入。
- 重入价格无法优于上一次开仓价，不重入。

## 第六部分：TP与雷达的共存关系

### 6.1 各层级分工

- TP1占10%，限价单由VPS挂出，价格到达即兑现。
- TP2占20%，限价单由VPS挂出，价格到达即兑现。
- TP3占70%，限价单由VPS挂出，价格到达即兑现。**雷达同时管理这70%仓位的止损**。

当TP3限价单先成交时，雷达止损立即撤销。当雷达止损先触发时，TP3限价单立即撤销。

### 6.2 互斥逻辑

TP3限价单和雷达止损单指向同一份仓位（即70%仓位），二者必须互斥。当一条路径成交时，立即撤销另一条路径的挂单。本地状态表维护仓位所有权标记，防止两条路径同时触发导致超卖。

**竞态条件防护**：极端行情下（比如价格剧烈跳空），理论上存在两条订单几乎同时触发的可能。撤销请求如果返回"该订单已成交"，必须立即停止后续操作，记录严重告警日志，并触发一次强制持仓核对（查询交易所真实持仓，和本地状态表交叉验证，以交易所真实持仓为准并修正本地状态）。

### 6.3 部分成交处理

当TP1或TP2部分成交时，硬止损单、雷达止损单和TP3限价单的数量都必须同步更新为当前总头寸。**所有数量更新必须在一次原子操作中完成，不能分开执行导致中间状态不一致**——比如不能出现"硬止损数量已经改小，但雷达止损数量还是旧值"这种中间态被外部读取到的情况。

## 第七部分：重复挂单根本性防护

### 7.1 本地订单状态表

每个挂单生成一个唯一的订单标签，由品种、方向、价格、开仓时间、随机数组合生成SHA-256哈希。挂单前必须检查本地状态表，如果存在该品种任何未完成状态的订单标签，绝对不允许再次挂单。**无论交易所查询返回什么结果，只要本地状态表中有未完成的订单标签，就不执行新的挂单操作**。

### 7.2 挂单数量硬上限

任何时候该品种未成交挂单总数不得超过5笔。如果检查到超过5笔，立即触发严重告警，暂停该品种所有交易，人工介入处理。

### 7.3 操作原子性

所有涉及挂单状态变更的操作必须原子化执行。挂单、撤单、改单操作严格按照"先查状态、再执行、再更新状态、再核对"的流程执行。

## 第八部分：API限流与WebSocket分工

### 8.1 原则

REST API只用于下单、改单、撤单和定期对账。WebSocket用于实时价格监控和订单状态更新推送。查询类操作不得使用REST轮询，全部使用WebSocket推送。

### 8.2 具体分工

| 功能 | 使用方式 | 频率 |
|---|---|---|
| 价格监控 | WebSocket订阅 | 实时 |
| 订单成交检测 | WebSocket订单更新推送 | 实时 |
| 开仓挂单 | REST API | 按信号触发 |
| 改单和撤单 | REST API | 按需触发 |
| 持仓核对 | REST API | 每30秒一次 |
| 5分钟K线拉取 | REST API | 每次重入时拉取 |

### 8.3 限流防护

任何REST API调用失败时采用指数退避重试策略。单个品种的REST请求间隔不得小于100毫秒。如果触发API限流错误，立即暂停该品种所有操作，等待限流窗口结束后再继续。

## 第十三部分：给Cursor的最终指令

### 13.1 核心原则

- 本地状态表是唯一真相源。任何查询失败都不允许默认"没挂单"然后重新挂单，必须等待下一次查询周期或触发告警。
- 每个品种同时存在的未成交挂单总数不得超过5笔。
- 每笔挂单必须有唯一的订单标签，标签在本地状态表中追踪全程。
- 任何操作都遵循"先查状态、再执行、再更新状态、再核对"的流程。
- **宁可错过，不要做错。**

### 13.2 实施顺序

1. 先清理旧逻辑（包括本版新增的两处：分档呼吸垫、错误的TP1×0.85实现），确保无残留后再实现新功能。
2. 实现硬止损动态计算和统一呼吸垫系数（1.15）。
3. 实现雷达延迟启动（按距离公式）和被动跟踪，区分首次开仓（0.85）与重入开仓（1.00）两种启动阈值。
4. 实现重入机制，最多一次。
5. 实现TP1、TP2、TP3与雷达的互斥逻辑。
6. 更新钉钉通知。
7. 完成测试验证（本地→模拟盘20U→实盘小仓位）。

### 13.3 最终交付要求

## 第十四部分：一句话总结

硬止损是底线，呼吸垫统一1.15不分档。雷达是骑士，首次开仓走到TP1距离85%时接管，重入开仓要走满100%才接管，两者都是按"距离"计算、锚定VPS实际成交价，不是直接对TP1绝对价格做乘法。弱趋势收紧，强趋势放宽，跟踪参数按档位自适应，但止损呼吸垫不再重复分档。重入收紧到最多一次，有窗口期限制，价格必须优于上一次开仓价，重入后雷达系数放宽一档、启动阈值也放宽到100%。TP3限价单与雷达止损互斥，谁先触发谁执行。重复挂单被本地状态表坚决阻止，查询不到状态时宁可放弃也不冒险。旧代码全部清理无残留，本版两处修正（分档呼吸垫、TP1阈值误读风险）已在第九部分列入清理清单。双币种独立运行互不干扰。等待真实TV信号到达，系统将自动执行完整流程。
