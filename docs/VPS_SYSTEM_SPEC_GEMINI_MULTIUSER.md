## 第一部分：设计哲学

### 1.1 核心思想

策略回测已经证明方向判断和胜率没有问题（ETH盈利因子14.177，XAU盈利因子15.393）。真正限制利润的是执行层过早干预，而不是策略本身的问题。

因此雷达的角色是**被动跟随、守护趋势**，不是主动锁利。入场靠TV评分系统，出场的利润兑现靠TP结构，雷达的职责是防止趋势被过早打断，而不是频繁判断方向。

**在多用户系统里，这套设计哲学对每一个用户账户都是独立生效的**——TV策略只产生一份信号，但每个用户的仓位、止损、雷达、重入状态，都是各自独立的一套完整实例，不共享，不互相影响。

### 1.2 五个层级各司其职

| 层级 | 职责 |
|---|---|
| TV策略 | 总指挥，判断方向、决定入场和出场时机（对所有用户是同一份信号） |
| 硬止损 | 最后防线，确保任何情况下单笔亏损可控（每个用户独立计算，因为每个用户的实际成交价不同） |
| TP1/TP2/TP3 | 利润兑现，逐级兑现利润，TP3占70%负责大肉部分（每个用户独立挂单） |
| 雷达 | 骑士守卫，TP1之前不介入，TP1之后跟随趋势上移止损，不主动判断方向（每个用户独立运行一套雷达实例） |
| 重入机制 | 补救措施，仅在雷达被噪音扫出时触发一次（每个用户独立判断，可能出现有的用户触发重入、有的用户没有触发的情况，这是正常的，不是bug） |

### 1.3 为什么TP3占比70%

TP1和TP2负责兑现小利润，TP3负责搏大趋势。如果TP3占比太低，大趋势来临时只有少量仓位能吃到利润。高占比的TP3让策略在趋势行情中有足够的仓位暴露，同时通过雷达的动态保护来控制回撤风险。

### 1.4 不再神经质的雷达

雷达不再提前介入、不再快速上移止损、不再频繁判断要不要走。价格走到TP1附近才启动，在TP1到TP2之间保持宽松跟踪，在TP2到TP3之间逐步收紧，在TP3之后转为动态追踪直到趋势终结。

## 第二部分：Webhook消息接收与鉴权

### 2.1 TV发送的两类消息

**开仓消息**（LONG或SHORT），包含字段：`secret`（鉴权）、`action`（LONG/SHORT）、`symbol`（品种代码）、`price`（开仓参考价）、`atr`（当前ATR值）、`stop_loss`（止损价）、`tp1`、`tp2`、`tp3`（三级止盈价）、`bot_id`（机器人标识）。

**反转保护消息**（CLOSE_QUICK_EXIT或CLOSE_RSI_EXIT），包含字段：`secret`、`action`、`symbol`、`price`（平仓参考价）、`reason`（触发原因）、`bot_id`。

**注意：这一份Webhook消息，是TV策略广播出来的唯一一份信号，不区分用户。多用户系统收到之后，需要在VPS这一层完成"分发给每一个用户账户"的路由逻辑，见第三部分。**

### 2.2 鉴权

VPS收到Webhook后，首先验证`secret`字段是否等于约定值，如果不匹配则拒绝处理整个信号（不分发给任何用户），只记录一条安全日志。

## 第三部分：多用户状态隔离与信号路由（本文档核心新增章节）

### 3.1 核心设计原则

**一份TV信号，多份独立执行。** VPS收到一条Webhook消息后，需要遍历当前所有"已启用该品种交易"的用户账户，对每一个用户账户，独立、完整地执行一遍第四部分到第十二部分描述的全部流程（清场、仓位计算、硬止损计算、挂止盈单、雷达初始化、重入判断等）。

**用户与用户之间完全隔离**，包括但不限于：

- 用户A的持仓状态、雷达档位、重入次数，不影响用户B的对应状态。
- 用户A的开仓因为保证金不足被拒绝，不影响用户B正常开仓。
- 用户A触发了重入，用户B没有触发（因为用户B的实际成交价、雷达激活时机可能因交易所、滑点不同而不同），这是完全正常的现象。
- 用户A使用的是币安，用户B使用的是OKX，两边的API调用、订单格式、异常处理细节可能不同，但整体流程逻辑必须一致。

### 3.2 状态存储结构

状态存储的键（key），必须同时包含**用户标识、交易所标识、品种标识**三个维度，缺一不可：

```
state[user_id][exchange][symbol] = {
    position: {...},
    tier: 0/1/2,
    radar_status: {...},
    reentry_count: 0/1,
    pending_orders: [...],
    api_credentials_ref: "..."   // 指向该用户在该交易所的API密钥配置，不直接存明文密钥在状态表里
}
```

同一个用户，如果在两个不同交易所都开通了账户（比如同时在币安和OKX交易），这两份账户的状态也要完全独立，不能因为是同一个用户就共享状态。

### 3.3 信号分发流程

1. Webhook消息鉴权通过后，VPS查询"用户-交易所-品种"配置表，找出所有**已启用**该`symbol`交易的用户账户列表。
2. 对列表中的每一个用户账户，**并发**（不是串行等待）发起一次完整的处理流程（第四部分到第十二部分）。用户数量多的时候，串行处理会导致后面的用户执行延迟过大，价格可能已经明显偏离信号发出时的水平。
3. 每个用户账户的处理流程互相独立，一个用户的处理失败（比如交易所异常）**不能阻塞或影响其他用户的处理**。
4. 所有用户处理完成后，汇总执行结果（成功/失败/异常），生成一条汇总日志和汇总钉钉通知（谁开仓成功、谁失败、失败原因分别是什么）。

### 3.4 用户配置的启用与禁用

每个用户账户针对每个品种，应该有一个独立的"是否启用"开关。如果某个用户暂时禁用了ETH交易，收到ETH的开仓信号时，直接跳过该用户，不产生任何交易动作，也不需要在汇总通知里特别提及（避免通知噪音）。

### 3.5 新增用户或用户配置变更的生效时机

新增用户账户、或者用户变更了启用品种/交易所配置，**只在下一次新的TV信号到达时生效**，不会去中途接管其他用户已经在运行中的历史仓位。这个设计避免了"半路加入一个仓位管理"带来的状态不一致风险。

## 第四部分：开仓消息处理流程（每个用户账户独立执行本部分全部步骤）

### 4.1 第一步：清场确认

对当前处理的用户账户，查询该用户在该交易所、该品种下的当前持仓状态。如果有持仓，执行市价全平。查询该用户所有未成交挂单，全部撤销。确认持仓归零，确认挂单列表为空。清场完成后，才能进入下一步。

### 4.2 第二步：仓位计算

VPS独立为该用户计算下单数量，不依赖TV消息中的任何数量字段，也不参考其他用户的仓位大小。

```
下单数量 = 该用户账户权益 × 20% × 5 / 开仓价
```

同时不超过该用户设置的最大杠杆限制（不同用户的杠杆偏好可能不同，需要从用户配置里读取，不是全局统一值）。

### 4.3 第三步：硬止损计算

```
第一步：计算TV止损距离（所有用户共用同一份TV信号，这一步计算结果相同）
tv_stop_distance = abs(webhook消息.price - webhook消息.stop_loss)

第二步：叠加呼吸垫系数（统一1.15，不分档位，见4.4说明，所有用户统一使用同一个系数）
actual_stop_distance = tv_stop_distance × 1.15

第三步：以该用户账户的实际成交价为锚点计算硬止损价（不同用户实际成交价可能不同，这一步结果因用户而异）
多单：硬止损价 = 该用户实际成交价 - actual_stop_distance
空单：硬止损价 = 该用户实际成交价 + actual_stop_distance
```

**数值算例**：假设用户A和用户B都收到同一条ETH多单信号，`price=1900.00`，`stop_loss=1874.00`。
- `tv_stop_distance = |1900.00 - 1874.00| = 26.00`（两个用户相同）
- `actual_stop_distance = 26.00 × 1.15 = 29.90`（两个用户相同）
- 用户A实际成交价`1900.80`，用户B因为用的是不同交易所、成交价`1901.20`
- 用户A硬止损价 = `1900.80 - 29.90 = 1870.90`
- 用户B硬止损价 = `1901.20 - 29.90 = 1871.30`

两个用户的硬止损价**不同**，这是正常现象，因为锚点是各自的实际成交价，不是统一的TV信号价。

### 4.4 呼吸垫系数说明（统一值，不分档位，也不分用户）

呼吸垫系数固定为**1.15**，适用于所有用户、ETH和XAU两个品种、所有强弱趋势档位，不按档位查表，也不按用户单独设置。

原因：TV策略这边的止损距离本身已经按趋势强弱分档，这是策略层面对行情性质的判断。VPS这层呼吸垫的本意是补偿"K线闭合发出信号"到"VPS实际完成开仓"这段执行链路的滞后与滑点，这是执行层面的固定摩擦，和趋势强弱、和具体是哪个用户都没有直接关系。

这个1.15是起始值，需要在第十五部分15.3节的实盘验证阶段用真实滑点数据校准（建议汇总所有用户的真实滑点数据一起校准，而不是每个用户单独校准出不同的系数，除非后续发现不同交易所之间滑点差异很大，才考虑按交易所细分这个系数）。

### 4.5 第四步：挂出止盈单

对该用户账户：

```
挂出TP1限价单，数量 = 该用户总仓位 × 10%，价格用webhook消息.tp1
挂出TP2限价单，数量 = 该用户总仓位 × 20%，价格用webhook消息.tp2
TP3不挂限价单，剩余70%仓位完全交给该用户的雷达管理（这一条不再有例外，详见第七部分本版最终修正）
```

注意所有用户使用的`tp1`/`tp2`/`tp3`价格都是**同一份TV信号里的值**，只有数量因各自仓位大小不同而不同。

### 4.6 第五步：初始化雷达状态

为该用户记录开仓价、当前ATR、当前档位，启动实时价格监控。此时该用户的雷达处于"未激活"状态，只有硬止损在保护该用户的仓位。

### 4.7 异常处理

- 如果Webhook消息中没有`stop_loss`字段，或字段值为零或负数，**对所有用户禁止开仓**并记录错误日志（这是信号本身的问题，不是某个用户的问题）。
- 如果计算出的`tv_stop_distance`小于该品种最小价格变动单位的5倍，同样对所有用户拒绝开仓并记录日志。
- 如果某个特定用户在下单环节遇到问题（比如该用户保证金不足），**只影响这一个用户**，不影响其他用户的正常开仓，处理方式见第十三部分。

## 第五部分：反转保护消息处理流程

收到`CLOSE_QUICK_EXIT`或`CLOSE_RSI_EXIT`消息时，VPS对**每一个已启用该品种的用户账户**独立执行：

1. 立即市价平掉该用户在该品种上的全部剩余仓位。
2. 撤销该用户该品种所有未成交挂单。
3. 重置该用户该品种的所有雷达状态和重入状态。
4. 记录日志，包含用户标识、交易所标识、平仓原因。

一个用户平仓失败（比如网络问题），不阻塞其他用户的平仓操作，失败的用户单独重试并告警。

## 第六部分：雷达止损引擎工作逻辑（每个用户独立运行一套雷达实例）

### 6.1 启动机制（本版再次修正：激活门槛大幅后移，雷达使命收窄为只守护TP1-TP2中点之后的行情）

**设计原则调整**：TP1（10%仓位）和TP2前半段的利润兑现，交给已经反复验证过的永久硬止损、以及TP1/TP2各自独立的限价单去守护，雷达完全不插手这一段。雷达的使命收窄为专注保护"更晚期、更大级别"的利润（从TP1-TP2区间中点开始，一路到TP3及以后）。这个原则对所有用户统一生效。

**为什么这么改**：
1. TP1只占10%仓位，雷达在这一段过度敏感所冒的"提前误伤剩余70%大仓位"的风险，远大于它所能保护的这10%收益。
2. 强趋势行情经常一根K线直接推穿TP1、TP2，不给"温和回调"的机会——雷达如果在这一段就介入判断，反而容易被单边行情里的正常波动误伤出局。而重入机制本来就只留给强趋势（见第九部分），强趋势往往一去不回头，被误伤出局后很难拿到比原信号更优的价格重新进场，反而错过了真正的大行情。
3. TP1、TP2的限价单本身独立于雷达运作，价格到了照样正常成交，不受雷达是否激活影响。

**新公式（改用绝对价格锚定，TP1/TP2对所有用户是同一份TV信号里的同一个价格，不因用户不同而不同）**：

```
第一步：直接取TP1、TP2的绝对价格（来自webhook消息的tp1、tp2字段，所有用户共用同一份信号，这一步结果所有用户相同）

第二步：根据开仓类型确定激活价格
首次开仓：
    多单：雷达激活价格 = (TP1价格 + TP2价格) / 2
    空单：雷达激活价格 = (TP1价格 + TP2价格) / 2
重入开仓：
    多单：雷达激活价格 = TP2价格
    空单：雷达激活价格 = TP2价格

第三步：激活条件（每个用户独立检查，但由于激活价格所有用户相同，理论上会在同一个市场价位同时触发，除非某个用户的行情数据源存在延迟）
多单：当前价格 >= 雷达激活价格 时，该用户雷达介入
空单：当前价格 <= 雷达激活价格 时，该用户雷达介入
```

**数值算例（首次开仓）**：ETH多单，`tp1=1925.65`，`tp2=1955.00`。
- `雷达激活价格 = (1925.65 + 1955.00) / 2 = 1940.325`（所有用户相同）

**数值算例（重入开仓）**：`雷达激活价格 = tp2 = 1955.00`，必须价格真正到达TP2，该用户雷达才会介入。

在价格到达启动条件之前，雷达完全不介入，只有硬止损在保护该用户的仓位，TP1、TP2各自的限价单照常独立运作。价格到达启动条件时，雷达接管该用户仓位，并将止损从硬止损位置上移至该用户实际入场价（首次开仓用首次成交价，重入用重入成交价）加减0.5倍ATR，之后按第6.2节的跟踪参数继续推进。

### 6.2 跟踪机制

雷达激活后，价格每涨一段，止损就跟进一段。跟踪步长和每次跟进幅度由当前档位决定（所有用户使用相同的档位参数表，因为档位是根据TV信号的ATR/止损距离判断的，与用户无关）：

**ETHUSDT.P**

| 档位 | 跟踪步长 | 每次跟进幅度 |
|---|---|---|
| 弱趋势 | 0.4倍ATR | 0.25倍ATR |
| 中趋势 | 0.5倍ATR | 0.35倍ATR |
| 强趋势 | 0.6倍ATR | 0.4倍ATR |

**XAUUSDT.P**

| 档位 | 跟踪步长 | 每次跟进幅度 |
|---|---|---|
| 弱趋势 | 0.35倍ATR | 0.2倍ATR |
| 中趋势 | 0.4倍ATR | 0.3倍ATR |
| 强趋势 | 0.5倍ATR | 0.35倍ATR |

### 6.3 呼吸空间动态调节

**ETHUSDT.P**

| 区间 | 弱趋势 | 中趋势 | 强趋势 |
|---|---|---|---|
| TP1到TP2 | 0.8倍ATR | 1.2倍ATR | 1.5倍ATR |
| TP2到TP3 | 1.0倍ATR | 1.6倍ATR | 2.0倍ATR |
| TP3之后 | 1.2~1.5倍ATR | 2.0~2.5倍ATR | 2.5~3.5倍ATR |

**XAUUSDT.P**

| 区间 | 弱趋势 | 中趋势 | 强趋势 |
|---|---|---|---|
| TP1到TP2 | 0.7倍ATR | 1.0倍ATR | 1.3倍ATR |
| TP2到TP3 | 0.9倍ATR | 1.4倍ATR | 1.8倍ATR |
| TP3之后 | 1.0~1.3倍ATR | 1.8~2.2倍ATR | 2.2~3.0倍ATR |

### 6.4 雷达与硬止损的关系

两笔止损单同时存在，各自独立运作。价格触发雷达止损时，该用户仓位归零后其硬止损自动撤销。价格直接击穿硬止损时，该用户仓位归零后其雷达止损自动撤销。两层保护互不干扰，谁先触发谁执行——这个判断是每个用户独立进行的。

## 第七部分：TP与雷达的共存关系（本版最终修正：TP3永远不挂限价单，VPS不再独立拉取ATR）

**修正说明（最终结论）**：此前版本文档一度把"TP3挂限价单、与雷达互斥"写成恒定规则，后来又尝试过"VPS拉取真实ATR成功才不封顶"的场景切换设计。**这两版都不是最终方案——币安没有和ETH策略周期（90分钟）匹配的原生K线，VPS想独立拉取一个和TV口径一致的真实ATR，只能靠拼接更小周期K线合成，边界一旦和TV的90分钟对不齐，算出来的数字照样会偏差，这条路走不通。**

**本版最终规则**：
1. **TP3永远不挂限价单，永远完全交给雷达管理，没有价格天花板，让它跟着趋势走到力竭为止。这一条对所有用户统一生效，不再有任何例外或场景切换。**
2. **VPS完全不再尝试独立拉取或计算真实ATR。所有需要用到ATR的地方（雷达跟踪步长、每次跟进幅度、呼吸空间），统一直接使用webhook消息里的`atr`字段（TV传来的值，所有用户共用同一份信号里的同一个数字）。**

这么做的理由：TV这套评分系统的方向判断质量已经被反复验证过，ATR也是这套体系里一直在用、被信任的数字，没有必要再让VPS另起一条自己都拿不准的数据链路。只用一个数据源，意味着"数据对不上"这类问题从设计上就不会再出现。

### 7.1 各层级分工

对每个用户，TP1占10%、TP2占20%，均独立挂出限价单，价格到达即兑现。TP3占70%，**永远不挂限价单**，完全交给雷达管理该用户这部分仓位的退出，雷达是这70%仓位唯一的主动退出路径（硬止损作为最后防线始终并存）。雷达的跟踪参数计算，所有用户统一使用同一份TV信号里的`atr`字段。

### 7.2 部分成交处理与动态头寸核算（本版大幅扩写，按用户独立执行）

**背景**：实盘中TP1、TP2这两笔限价单，**不一定是一口气整笔成交的**——交易所撮合引擎可能把一笔挂单拆成多次部分成交，也可能因为深度不足导致某一档长时间只成交一部分。这意味着**每个用户的总持仓头寸会随着实盘推进持续、细微地变化**，且不同用户的成交节奏可能完全不同（同一份信号，不同用户的部分成交进度不同步是正常现象）。

**核心规则：对每个用户，任何一笔挂单（TP1/TP2/硬止损/雷达止损）只要发生任何数量变化的成交回报，都必须立即触发一次针对该用户的头寸重新核算，不能只在"整笔成交"这种大事件时才更新，也不能因为其他用户的成交状态而误算到当前用户身上。**

**重新核算流程（每个用户独立执行）**：

1. 收到该用户的WebSocket订单成交回报（含部分成交）后，更新该用户本地记录的"当前总持仓头寸"。
2. 立即重新计算该用户硬止损单、雷达止损单（如果已激活）当前应有的挂单数量 = 更新后该用户的总持仓头寸。
3. 如果数量不一致，立即为该用户发起改单操作，同步止损单数量。操作必须原子化，先记录"待同步"、执行、成功后更新为"已同步"，失败则重试。
4. 雷达止损价格的计算不受头寸数量变化影响，只有挂单"数量"字段需要同步。

**为什么这一步很重要**：如果止损单数量没有跟着实际头寸缩小而同步缩小，一旦触发会导致平仓数量超过实际持仓，**平仓变成反向开仓**。处理方式见第十部分10.5。

### 7.4 平仓操作前必须核实交易所真实持仓（本版新增，按用户独立执行）

任何触发平仓的场景，**在为某个用户执行平仓下单之前，必须先用REST API查询该用户在对应交易所的真实持仓数量作为最终依据，不能仅凭本地状态表的记录直接计算平仓数量**。

平仓下单数量必须以查询到的该用户真实持仓数量为准，且**设置硬上限——绝对不能超过查询到的真实持仓数量**，宁可少平，不能多平变成反向开仓。**这个核实过程按用户独立执行，不能用其他用户的持仓数据代替。**

## 第八部分：VPS重启状态恢复（新增章节，多用户场景需逐用户恢复）

### 8.1 设计原则

VPS可能因为服务器维护、程序崩溃、网络中断等原因意外重启。**重启后，所有用户正在运行中的仓位都不能失去保护**。多用户场景下，恢复流程需要对**每一个有持仓的用户账户**逐一执行，不能只恢复部分用户。

**核心原则：所有影响仓位安全的状态，必须持久化存储，且必须以"用户-交易所-品种"为最小恢复单元。**

### 8.2 需要持久化的状态清单

对每一个用户账户的每个品种，以下状态必须写入本地数据库或文件，且每次状态变更后立即落盘：

- 用户标识、交易所标识
- 当前持仓方向、数量、开仓均价、开仓时间
- 当前档位（弱/中/强）
- 硬止损价格、硬止损订单ID
- 雷达是否已激活、雷达当前止损价格、雷达订单ID
- TP1/TP2限价单的订单ID、剩余数量、是否已成交（TP3无限价单，不适用）
- 当前重入次数（0或1）
- 本地订单状态表的完整快照

### 8.3 重启恢复流程

1. VPS服务启动时，**先不做任何交易操作**，读取本地持久化状态，得到"当前有持仓或有效状态的用户账户列表"。
2. 对列表中**每一个用户账户**（并发执行，不要串行等待，避免用户数量多时恢复时间过长）：
   - 查询该用户在对应交易所的真实持仓和真实挂单列表，与本地状态交叉核对。
   - 一致则恢复该用户的雷达/重入状态，继续正常监控。
   - 不一致则以交易所真实状态为准，修正本地记录；如果发现该用户有持仓但缺少止损保护，**立即为该用户重新挂出硬止损单，这是最高优先级动作**。
   - 记录该用户的恢复结果（正常/修正/异常）到日志。
3. 所有用户的恢复流程都完成、且都确认止损保护到位后，才恢复正常的价格监控和新信号接收。
4. **单个用户恢复失败，不阻塞其他用户的恢复**——比如用户A对接的交易所在恢复期间恰好也不可用，用户A进入"待人工介入"状态，但用户B、用户C的恢复流程正常继续，不受影响。
5. 汇总所有用户的恢复结果，生成一条汇总日志和钉钉通知（多少用户正常恢复、多少用户状态被修正、多少用户需要人工介入）。
6. 如果超过合理时间（建议按用户数量弹性调整，比如每用户5秒预算）仍有用户未完成恢复，对未完成的用户单独触发严重告警，其余已完成的用户不受影响、正常运行。

### 8.4 恢复期间的Webhook处理

VPS重启后的恢复流程执行期间，如果收到新的TV信号，**先缓存该信号，不立即处理**。等**全部用户**的恢复流程完成后，才按正常流程分发处理缓存的信号。如果信号已经过期太久（比如超过5分钟），可以选择丢弃并记录日志。

## 第九部分：重入机制（每个用户独立判断，可能出现不同用户结果不同）

### 9.1 触发条件（每个用户独立核对，必须同时满足，本版新增第5、6条）

1. 该用户平仓来源是雷达扫出，**硬止损扫出绝对不触发该用户的重入**。
2. 该用户平仓价格落在允许区间内：ETH多单为该用户开仓价到开仓价+0.5倍ATR，XAU多单为该用户开仓价到开仓价+0.3倍ATR，空单对称（注意这里用的是"该用户"自己的开仓价，不是TV信号价，因为不同用户实际开仓价不同）。
3. TV信号仍然有效，未收到反向信号或平仓信号（这一条对所有用户是共同的判断依据）。
4. 该用户在该方向信号下累计重入次数为零（最多一次）。
5. **【本版新增】该用户的TP1限价单尚未成交。** 如果价格曾经到达过TP1、该用户这笔仓位10%的TP1限价单已经成交过，即使后续雷达止损被触发、且触发价格恰好也落在条件2的允许区间内，**也不允许该用户重入**。原因：条件2检查的只是"最终触发止损那一刻的价格"，不检查"这笔交易历史上是否已经走到过TP1"，"冲高到TP1成交后又回落回到接近保本位置"这种情况说明趋势已经得到过真实确认后又反转，不属于"刚起步就被噪音扫出"的场景。**这个判断按用户各自独立核对**，因为不同用户的TP1是否成交、成交时机可能因实际成交价差异而略有不同。
6. **【本版新增】该笔信号的持仓档位必须是强趋势（tier=2）。** 弱趋势（tier=0）和中趋势（tier=1）档位下的雷达扫出，一律不触发重入。重入机会只留给最有把握的强趋势场景。**由于档位是根据TV信号本身的ATR/止损距离判断的，与具体哪个用户无关，所有用户在同一笔信号下使用同一个档位判断结果**，不会出现"用户A判定强趋势允许重入、用户B判定中趋势不允许"这种不一致。

### 9.2 重入窗口期

ETH窗口期2根K线（约3小时），XAU窗口期3根K线（约2.25小时）。每个用户独立计时，从该用户被雷达扫出的那一刻开始算起（不是所有用户统一从TV信号发出时刻算起，因为不同用户被扫出的时刻可能不同）。超过窗口期放弃该用户本轮重入。

### 9.3 重入价格计算（本节为精确定义，替代此前的模糊表述）

```
多单重入价 = min(最近一根已收盘的5分钟K线的最低价 + 1个tick, TV信号价 × 0.997)
空单重入价 = max(最近一根已收盘的5分钟K线的最高价 - 1个tick, TV信号价 × 1.003)
```

**精确定义澄清**："最近一根已收盘的5分钟K线"指的是**在计算这一刻，时间上最近的、已经完整走完的一根5分钟K线**，不是过去若干根K线里的最低/最高值，也不是当前正在形成中的未收盘K线。每次挂单超时被撤销、需要重新计算价格时，都要重新拉取"当时那一刻"最新的一根已收盘5分钟K线，不能沿用上一次计算时的旧数据。

**多用户场景补充说明**：如果多个用户在同一个交易所，5分钟K线数据可以共用一份拉取结果，不需要每个用户单独拉取一次（减少不必要的API调用）；如果用户分布在不同交易所，则需要按交易所分别拉取（不同交易所的价格可能有细微差异）。

如果5分钟K线数据不可用，使用3分钟K线作为备选，定义方式相同。**重入价格必须优于该用户上一次开仓价，否则不触发该用户的重入。**

### 9.4 重入后的雷达系数与启动阈值

该用户重入成功后，跟踪步长和每次跟进幅度使用比首次开仓宽松一档的参数。雷达启动阈值固定使用"到达TP2价格"。档位递进只在该用户重入成功时发生，不影响TP1、TP2、TP3限价单的价格和数量。

### 9.5 不允许重入的情况

硬止损平仓绝对不重入；亏损平仓不重入；TV已发出平仓或反向信号时不重入；超过窗口期不重入；已经重入过一次不重入；重入价格无法优于上一次开仓价不重入；**该用户TP1限价单已经成交过不重入（本版新增）**；**当前档位不是强趋势（弱趋势或中趋势）不重入，此条对所有用户统一生效（本版新增）**。这些条件对每个用户独立判断（第6条除外，因为档位判断和用户无关）。

## 第十部分：重复挂单根本性防护与平仓完整性保障（按用户-交易所-品种维度隔离）

### 10.1 本地订单状态表

每个挂单生成唯一订单标签，由**用户标识、交易所标识、品种、方向、价格、开仓时间、随机数**组合生成SHA-256哈希（比单账户版多了用户和交易所两个维度，确保不同用户的订单标签不会冲突）。挂单前必须检查本地状态表，如果存在该用户该品种任何未完成状态的订单标签，绝对不允许再次为该用户挂单。

### 10.2 明确点名历史bug模式，作为反面案例

**此前出现过的具体故障模式**：查询持仓接口失败或超时，代码没有正确处理这个失败，而是默认"查询不到=没有挂单"，于是继续执行挂单逻辑，导致同一个价位被反复挂出几十笔一模一样的限价单，堆积在盘口上。**这个模式必须被彻底杜绝**，在多用户场景下尤其要注意——一个用户查询失败导致的重复挂单风暴，绝不能因为代码共用逻辑而蔓延影响到其他用户。具体规则：

- 任何查询操作返回失败、超时、或返回内容不完整/格式异常，**一律视为该用户"状态未知"，不允许当作"无持仓"或"无挂单"处理**。
- 状态未知时唯一允许的动作是重试查询或达到重试上限后告警暂停**该用户**该品种操作，绝不允许在状态未知情况下为该用户挂单。
- 本地状态表（按用户-交易所-品种维度）的"未完成订单标签"是判断"要不要挂单"的唯一依据。

### 10.3 挂单数量硬上限

**每个用户账户**、每个品种，未成交挂单总数不得超过5笔（这个上限是按用户单独计算的，不是全系统汇总）。超过立即触发针对该用户的严重告警，暂停该用户该品种的所有交易，人工介入，不影响其他用户。

### 10.4 平仓完整性验证（本版新增，按用户独立执行，杜绝幽灵单、蚂蚁单、反向单）

**核心原则：为某个用户执行任何一次平仓动作后，必须立即验证该用户该品种的盘口已经清理干净，不能只是"发出了撤单请求"就算完事。**

**数量精度处理（蚂蚁单的另一个根源，本版新增）**：对每个用户，TP1/TP2拆分和部分成交剩余数量的计算，都可能出现不满足该用户所在交易所最小下单量或最小名义价值要求的"零头"。处理规则：拆分TP1/TP2数量时按精度向下取整，多出来的零头并入TP3对应的雷达管理仓位；如果TP1/TP2部分成交后剩余数量小于最小下单量，无法再挂对应的限价单，**直接对这部分零头执行市价平仓**，不让它以挂单形式滞留。

具体流程（对每个用户独立执行）：

1. 该用户的平仓执行完成后，**立即撤销该用户该品种所有还在挂着的关联订单**——TP1/TP2剩余部分、硬止损单、雷达止损单，一个都不能漏。
2. 撤单请求发出后，**必须再查询一次该用户该品种的未成交挂单列表，确认列表为空**。不为空则对剩余订单逐一撤销，直到确认清空。
3. 如果连续3次查询仍有残留订单，触发针对该用户的严重告警，人工介入，**该用户该品种暂停接受新的开仓信号，其他用户不受影响**。
4. 特别注意"蚂蚁单"（多次部分成交、拆单、精度舍入产生的极小额残留订单）——验证盘口清空时，任何数量大于零的挂单都算作残留。

### 10.5 防止"多余份量的限价单变成反向单"（本版新增）

如果某用户平仓时下单数量计算错误（比如没有按7.4的要求用交易所实时查询的真实持仓做上限），**平仓下单数量可能超过该用户实际持仓量**，超出部分会直接开出一笔反方向的新仓位。

**强制规则（按用户独立执行）**：

- 任何用户的平仓下单，数量必须严格等于（不能大于）7.4中查询到的该用户交易所真实持仓数量。
- 下单前必须有显式数值比较：`该用户平仓下单数量 <= 该用户交易所真实持仓数量`，不成立则直接拒绝执行，触发告警，不做四舍五入等模糊处理。
- 该用户平仓成交后，按10.4流程核对持仓是否真的归零；如果发现持仓方向翻转，说明发生了超卖变反向单的严重故障，**立即触发针对该用户的最高级别告警，暂停该用户该品种所有自动化操作，其他用户不受影响，需要人工介入手动处理该用户这笔异常仓位**。

### 10.6 平仓操作的幂等性

对每个用户，平仓这个动作本身需要幂等保护：如果因为竞态条件（比如TP成交事件和反转信号几乎同时到达），同一个用户同一笔仓位的平仓请求被触发了两次，**第二次平仓请求必须先查询该用户当前持仓，如果已经是零持仓，直接判定为"已完成"、跳过本次操作**。

### 10.7 操作原子性

所有涉及挂单状态变更的操作严格按照"先查状态、再执行、再更新状态、再核对"的流程执行，且必须限定在单一用户的状态范围内操作，不能出现跨用户的状态污染。

## 第十一部分：API限流与WebSocket分工（多用户场景需考虑多交易所并发限流）

### 11.1 原则

REST API只用于下单、改单、撤单和定期对账。WebSocket用于实时价格监控和订单状态更新推送。查询类操作不得使用REST轮询。

### 11.2 具体分工

| 功能 | 使用方式 | 频率 |
|---|---|---|
| 价格监控 | WebSocket订阅（每个交易所一份订阅，多用户共用同一交易所的价格数据，不需要每用户单独订阅） | 实时 |
| 订单成交检测 | WebSocket订单更新推送（每个用户账户独立订阅自己的订单流） | 实时 |
| 开仓挂单 | REST API | 按信号触发，每用户独立调用 |
| 改单和撤单 | REST API | 按需触发，每用户独立调用 |
| 持仓核对 | REST API | 每用户每30秒一次 |
| 5分钟K线拉取 | REST API | 每次重入时拉取，同交易所多用户可共用一次拉取结果 |

### 11.3 限流防护（按交易所独立限流，不同交易所互不影响）

任何REST API调用失败时采用指数退避重试策略。**限流额度按"交易所"维度独立管理**，不是全局共享——比如币安的限流状态不影响OKX的调用。单个用户在单个交易所的请求间隔不得小于100毫秒。如果某个交易所触发限流错误，暂停**该交易所下所有用户**的操作，等待限流窗口结束后再继续，不影响其他交易所的用户。

### 11.4 多用户并发下单的实现建议

收到开仓信号后，对多个用户的下单请求，建议按"交易所"分组做并发控制——同一交易所内部的多个用户请求可以并发发出，但要遵守该交易所的限流上限（比如通过一个简单的令牌桶或队列机制控制并发度），不同交易所之间的请求互不干扰、完全并行。

## 第十二部分：钉钉通知（多用户场景需要区分用户）

### 12.1 通知内容清单

所有通知内容和币安单账户版一致（开仓、雷达激活、止损移动、TP成交、平仓、重入尝试、重入成交、重入放弃、重启恢复、异常处理），**但每条通知必须额外包含用户标识和交易所标识**，格式建议：

```
【品种标签】【用户标识】【交易所标识】事件类型：详细参数（含档位信息）
```

### 12.2 汇总通知（多用户场景新增）

每次TV信号触发的批量处理完成后，除了每个用户各自的独立通知外，**额外发送一条汇总通知**，包含：本次信号涉及的用户总数、成功执行数、失败/异常数（及失败用户列表和原因）。这条汇总通知帮助你快速掌握整体执行情况，不需要逐条翻阅每个用户的独立通知。

## 第十三部分：交易所异常处理（新增章节，按用户独立处理，不同用户可能对接不同交易所）

### 13.1 下单被拒绝（保证金不足等）

- 记录详细错误日志，包含**用户标识**、拒绝原因、尝试的订单参数。
- 不自动重试下单。
- 立即触发针对该用户的告警通知，暂停该用户该品种新开仓（已有持仓的止损/止盈单不受影响）。
- **不影响其他用户**，其他用户的开仓正常继续。
- 需要人工确认该用户账户资金状况后手动恢复。

### 13.2 交易所API临时不可用（网络超时、5xx错误等）

- 采用指数退避重试：首次立即重试，之后每次重试间隔翻倍，最多重试5次。
- **由于不同用户可能对接不同交易所，这个异常状态是按交易所维度判断的**：如果币安API不可用，只影响对接币安的用户，不影响对接OKX的用户。
- 5次重试均失败后，暂停**该交易所下所有用户**该品种的自动化操作，进入"仅监控不操作"模式。
- API恢复检测：每隔30秒尝试一次只读请求，成功后自动退出"仅监控"模式，并对该交易所下所有受影响用户执行一次持仓核对（参照第八部分8.3流程）。

### 13.3 订单被交易所单方面取消

- 检测方式：WebSocket订单状态推送收到"已取消"但本地状态表未曾主动发起撤销请求。
- 处理流程：立即触发针对该用户的严重告警日志。立即执行一次针对该用户的强制持仓核对。根据核对结果重新挂出必要的保护性订单（尤其止损单优先）。
- 如果**同一用户**在同一品种上短时间内（10分钟内）连续发生3次以上异常取消，暂停该用户该品种所有操作，人工介入。
- 如果**同一交易所下多个不同用户**在短时间内都发生异常取消，判定为交易所层面可能存在系统性问题，暂停该交易所所有用户该品种的操作，人工介入。

### 13.4 通用原则

任何交易所异常情况下，优先保证已有仓位的止损保护不丢失，其次才考虑是否继续新开仓或重入。异常处理必须精确定位到具体的"用户-交易所"维度，**避免一个用户的异常错误地影响到其他用户的正常运行**。

## 第十六部分：三端同步与部署

### 16.1 代码对齐要求

确认本地修改已提交并推送到GitHub对应分支。确认VPS上拉取的代码版本和GitHub最新版本一致。部署前记录当前VPS正在运行的旧版本commit hash，作为回滚基准点。部署后health检查通过，确认无异常告警。

### 16.2 部署步骤

1. 确认所有用户当前都没有持仓，或选择在所有用户都空仓的时间点部署（多用户场景下这个时间点更难协调，建议提前通知所有用户或选择低活跃时段）。

## 第十七部分：给Cursor的最终指令

### 17.1 核心原则

本地状态表是唯一真相源，且必须以"用户-交易所-品种"为最小单元。任何查询失败都不允许默认"没挂单"然后重新挂单。每个用户每个品种的未成交挂单总数不得超过5笔。每笔挂单必须有唯一订单标签（包含用户和交易所信息）。任何操作都遵循"先查状态、再执行、再更新状态、再核对"的流程，且严格限定在单一用户的状态范围内。**所有影响仓位安全的状态必须持久化，VPS重启不能让任何一个用户的在途仓位失去保护。一个用户的异常绝不能扩散影响其他用户。**宁可错过，不要做错。

### 17.2 实施顺序

1. 先清理旧逻辑（包括任何"全局共享状态"的设计残留），确保无残留后再实现新功能。
2. **实现多用户状态隔离与信号路由框架（第三部分）——这是整个多用户系统的地基，必须最先完成，后续所有功能都要基于这个框架开发，不能先按单用户实现再回头改造。**
3. 实现硬止损动态计算和统一呼吸垫系数（1.15）。
4. 实现雷达延迟启动（按TP1/TP2绝对价格锚定），首次开仓激活价格=(TP1+TP2)/2，重入开仓激活价格=TP2。
5. 实现状态持久化和多用户重启恢复流程（第八部分）。
6. 实现重入机制，最多一次，明确"最近已收盘5分钟K线"的取值逻辑，注意多用户场景下每个用户独立计时窗口期。
7. 确认TP3全程不挂限价单，完全交给雷达管理，删除任何"TP3限价单与雷达互斥"的旧代码，删除VPS独立拉取ATR的机制。
8. 实现交易所异常处理，注意按用户/交易所维度隔离影响范围。
9. 更新钉钉通知，包含单用户通知和汇总通知。
10. 完成测试验证（本地→模拟盘多用户20U，含重启测试和异常场景测试→实盘小仓位少量真实用户）。
11. 三端同步部署。

### 17.3 最终交付要求

代码必须通过所有测试场景验证，尤其是多用户隔离、重启恢复、交易所异常处理这三块内容。日志完整可追溯，且能按用户、按交易所筛选。钉钉通知区分品种、用户、交易所和事件类型，并有汇总通知。文档同步更新，包括README、部署文档、配置说明、用户配置管理说明。三端commit hash一致。

## 第十八部分：一句话总结

一份TV信号，广播给多个用户账户，每个用户在每个交易所的状态完全独立隔离，互不影响。硬止损是底线，呼吸垫统一1.15不分档、不分用户。雷达是骑士，但使命大幅收窄——TP1(10%)和TP2前半段完全交给硬止损与TP1/TP2限价单自己守护，雷达首次开仓要等价格走到TP1-TP2区间中点才接管，重入开仓要等价格真正到达TP2才接管，用TP1/TP2绝对价格直接锚定，所有用户共用同一份信号算出的同一个激活价格。TP3(70%)永远不挂限价单，没有价格天花板，完全交给雷达追到趋势尽头，雷达跟踪计算统一使用TV传来的atr字段，VPS不再尝试独立拉取真实ATR（币安没有和策略周期匹配的原生K线，这条路走不通）。重入最多一次，每个用户独立计时窗口期，价格必须优于该用户自己上次的开仓价，且只有该用户TP1从未成交过、当前档位是强趋势时才允许重入。VPS任何时候意外重启，所有用户的状态从持久化存储逐一恢复，止损保护必须在恢复流程的最高优先级完成，单个用户恢复失败不阻塞其他用户。交易所异常按用户/交易所维度隔离处理，一个用户或一个交易所的异常绝不扩散到其他用户。重复挂单防护、限流管理均以"用户-交易所-品种"为最小单元。旧代码全部清理无残留，尤其是任何全局共享状态的设计残留。等待真实TV信号到达，系统将自动为每一个已启用的用户账户执行完整流程。
